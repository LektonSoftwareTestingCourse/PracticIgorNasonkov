# Чек-листы СМП: дымовое тестирование и критический путь

> **Артефакт 2** — тестовая документация по СМП
> **Слой**: периферия (все сервисы; чек-листы задают перечень проверок без конкретных данных, шагов и ожидаемых результатов)
> **Основание**: [`docs/checklists.md`](../checklists.md) (чек-листы само-приёмки), [`docs/architecture.md`](../architecture.md), [`scripts/smoke-test.sh`](../../scripts/smoke-test.sh)
> **Техника**: checklist-based (лекция 3)

## 0. Назначение и область применения

Чек-лист — упорядоченный перечень проверок, определяющий, что подлежит проверке, но не содержащий конкретных входных данных, шагов и ожидаемых результатов. Ожидаемые результаты для тривиальных проверок здесь не приводятся; для нетривиальных указаны в скобках.

Для периферийных сервисов (Gateway, Switch, симуляторы, Bin Lookup, Notification Service, Transaction Logger, Web Dashboard) глубокий test-design не строится: их поведение проще, а глубокая модель не даёт соразмерного эффекта. Достаточно классов верхнего уровня и двух перечней ниже. Это соответствует риск-ориентированному тестированию: объём работ следует за риском.

**Классы верхнего уровня для периферии:**

| Сервис | Классы верхнего уровня |
|---|---|
| Gateway | маршрутизация по пути · валидация тела · rate-limit (99/100/101 req/s) · недоступность downstream (503) |
| Switch | BIN известный / неизвестный · ответ Authorization получен / таймаут · публикация в RabbitMQ подтверждена / не подтверждена |
| Terminal Simulator | сценарии `normal`, `mixed`, `high_value`, `night_time`, `declines_test` |
| Merchant Simulator | сценарии `grocery`, `electronics`, `restaurant`, `travel` · корректная комиссия 1–3 % |
| Bin Lookup | BIN известный / неизвестный · недоступность (graceful degradation) |
| Transaction Logger | запись создана / дубль `id` не создаётся · поиск с фильтрами · пагинация |
| Web Dashboard | данные получены / ошибка сети · real-time поток · фильтры |

## 1. Чек-лист дымового тестирования

Быстрая оценка работоспособности системы после сборки. Выполняется после каждого `docker compose up -d` и после развёртывания новой версии.

### 1.1. Инфраструктура и запуск

- [ ] `docker compose up -d` поднимает 11 сервисов + PostgreSQL + RabbitMQ без ошибок
- [ ] `docker compose ps` — все контейнеры в состоянии `Up` (healthy)
- [ ] `docker compose version` — Docker Desktop доступен
- [ ] PostgreSQL доступен на порту `5432`
- [ ] RabbitMQ AMQP доступен на порту `5672`
- [ ] RabbitMQ Management UI доступен на `http://localhost:15672` (логин `smp`/`smp`)

### 1.2. Health-check всех сервисов

- [ ] Gateway — `GET http://localhost:8080/health` → 200, все `services` = `ok`
- [ ] Card-Management — `GET http://localhost:8081/health` → 200
- [ ] Switch — `GET http://localhost:8082/health` → 200
- [ ] Authorization — `GET http://localhost:8083/health` → 200
- [ ] Merchant Simulator — `GET http://localhost:8084/health` → 200
- [ ] Terminal Simulator — `GET http://localhost:8085/health` → 200
- [ ] Transaction Logger — `GET http://localhost:8088/health` → 200
- [ ] Bin Lookup — `GET http://localhost:8096/actuator/health` → 200
- [ ] Notification Service — `GET http://localhost:8097/actuator/health` → 200
- [ ] Web Dashboard доступен на `http://localhost:3000`

### 1.3. Дымовые проверки данных и сквозного потока

- [ ] Обязательные эндпоинты отвечают 200/201 (без 500)
- [ ] Генерация тестовых карт: `POST /api/cards/generate` создаёт не менее 20 карт
- [ ] Список карт: `GET /api/cards?limit=50` возвращает непустой `cards`
- [ ] Запуск симулятора: `POST /api/simulator/terminal/run` `{count=50}` обрабатывает 50 транзакций
- [ ] Транзакции попадают в лог: `GET /api/transactions/search` возвращает записи
- [ ] Статистика доступна: `GET /api/dashboard/stats` возвращает непустой ответ
- [ ] WebSocket `/ws/transactions` принимает подключение и получает сообщения
- [ ] `./scripts/smoke-test.sh` завершается строкой `🎉 ALL CHECKS PASSED`
- [ ] После генерации карт и прогона симулятора в RabbitMQ нет сообщений в DLQ

## 2. Чек-лист критического пути

Проверка ключевых пользовательских сценариев процессинговой цепочки. В отличие от дымового теста проверяется корректность результатов, а не только доступность.

### 2.1. Критический путь 1: «Создание карты → Авторизация → Логирование → Дашборд»

- [ ] Карта создана: `POST /api/cards` → 201, PAN из 16 цифр валиден по Луне, `status = ACTIVE`
- [ ] Карта читается: `GET /api/cards/{pan}` → 200, поля соответствуют созданным
- [ ] Авторизация одобрена: `POST /api/transactions` со всеми валидными полями → `APPROVED`, `responseCode = "00"`
- [ ] Получены `rrn` (12 цифр) и `authCode` (6 символов)
- [ ] Баланс уменьшен ровно на сумму транзакции
- [ ] Транзакция записана: `GET /api/transactions/search?pan={pan}` → запись со `status = APPROVED`
- [ ] Транзакция отражена в дашборде: `GET /api/dashboard/recent` содержит её
- [ ] WebSocket-сообщение о транзакции получено клиентом (с учётом eventual consistency)
- [ ] `GET /api/dashboard/stats` — счётчики увеличены, `approvalRate` пересчитан

### 2.2. Критический путь 2: «Массовая генерация → Смешанный сценарий → Статистика»

- [ ] 100 карт сгенерированы и равномерно распределены по 5 BIN
- [ ] Сценарий `mixed` через `POST /api/simulator/terminal/run` выполнен
- [ ] Среди результатов есть и `APPROVED`, и `DECLINED` (соответствие ожиданиям сценария)
- [ ] Доля отклонений в пределах ожиданий сценария (заблокированные карты, превышение лимита)
- [ ] Все транзакции сценария зафиксированы в Logger (число записей совпадает с `totalSubmitted` с учётом retry)
- [ ] Статистика `GET /api/dashboard/stats` согласована: `approvedCount + declinedCount = totalTransactions`
- [ ] Гистограмма распределения сумм и график потока отрисованы в дашборде

### 2.3. Критический путь 3: «Отклонённые операции и целостность»

- [ ] Сценарий `declines_test` возвращает ожидаемые коды: `14`, `CARD_BLOCKED`, `51`, `61`
- [ ] Несуществующий PAN → `DECLINED`, `14` (не 500)
- [ ] Заблокированная карта → `DECLINED`, `CARD_BLOCKED`
- [ ] Недостаточный баланс → `DECLINED`, `51`
- [ ] Превышение дневного лимита → `DECLINED`, `61`
- [ ] При недоступности Logger (`Publisher Confirm` не получен) — резервирование откатывается, клиент получает `DECLINED`, `96`
- [ ] Ни одна одобренная транзакция не осталась без записи в очереди/логе
- [ ] Повторный `POST /api/internal/log` с существующим `id` не создаёт дубликат
- [ ] После серии отказов баланс карты консистентен (не отрицателен)

### 2.4. Критический путь 4: «Управление картой»

- [ ] `PATCH /api/cards/{pan}` меняет только переданные поля, остальные неизменны
- [ ] `DELETE /api/cards/{pan}` выполняет мягкое удаление (`status = DELETED`)
- [ ] Удалённая карта не возвращается в `GET /api/cards/{pan}` и `GET /api/cards`
- [ ] Авторизация по удалённой карте → `DECLINED`, `14`
- [ ] Изменение карты публикует событие и приводит к уведомлению в Notification Service
- [ ] Резервирование `POST /api/cards/{pan}/reserve` в пределах баланса уменьшает `availableBalance`

## 3. Связь чек-листов с test-design

| Слой | Что проверяет | Инструмент |
|---|---|---|
| Дымовое тестирование | работоспособность сборки, доступность всех сервисов | чек-лист + `scripts/smoke-test.sh` |
| Критический путь | ключевые сквозные сценарии процессинга | чек-лист + симуляторы |
| Test-design ядра | правила авторизации и CRUD, границы, комбинации | [`test-design.md`](test-design.md) |

Чек-листы описывают **что** проверяется на уровне периферии и сквозных сценариев; конкретные данные, шаги и ожидаемые результаты фиксируются тест-кейсами ядра в [`test-design.md`](test-design.md).
