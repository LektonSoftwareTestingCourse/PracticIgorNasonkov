## 1. Область, источники и схема идентификаторов

Test-design строится для двух сервисов ядра:

| Сервис | Порт | Проверяемые операции |
|---|---:|---|
| **Authorization** | 8083 | `POST /api/internal/authorize` — статус, срок действия, лимиты, баланс, резервирование |
| **Card-Management** | 8081 | `POST /api/cards`, `GET /api/cards/{pan}`, `GET /api/cards`, `PATCH /api/cards/{pan}`, `DELETE /api/cards/{pan}`, `POST /api/cards/generate`, `POST /api/cards/{pan}/reserve` |

Идентификаторы тест-кейсов:

| Префикс | Техника | Сервис |
|---|---|---|
| `TC-AUTH-` | классы эквивалентности | Authorization |
| `TC-AUTH-BV-` | граничные значения | Authorization |
| `TC-AUTH-PW-` | pairwise (строка набора) | Authorization |
| `TC-AUTH-MAN-` | ручное дополнение (критичные тройки) | Authorization |
| `TC-CM-` | классы эквивалентности | Card-Management |
| `TC-CM-BV-` | граничные значения | Card-Management |
| `TC-CM-PW-` | pairwise (строка набора) | Card-Management |
| `TC-CM-MAN-` | ручное дополнение | Card-Management |

**Порядок проверок в Authorization** (по [`tz/04-authorization.md`](../../tz/04-authorization.md), §2): карта найдена → статус → срок действия → дневной лимит → месячный лимит → доступный баланс → резервирование. Ожидаемый результат тест-кейса определяется **первой** сработавшей проверкой, поэтому в кейсах, где нарушено несколько условий, проверяется приоритет кода отказа.

**Порядок валидации в Card-Management** (принят для однозначности ожидаемых результатов):

1. **Формат пути** — `pan` в пути: ровно 16 цифр, только цифры → иначе `400`.
2. **Тело / фильтры** — для `create` и `patch`: `currencyCode` (только `643`), неотрицательные `dailyLimit`/`monthlyLimit`/`initialBalance`; для `reserve` тело — только `{amount, rrn}`, проверяется `amount > 0`; для `list`: `limit ≥ 0`, `offset ≥ 0`, `status` из списка → иначе `400`.
3. **Поиск карты** — карта существует и не `DELETED` → иначе `404`.
4. **Бизнес-правила** — для `reserve`: статус `ACTIVE` и не истёкший срок → иначе `422`; для `delete`: уже удалённая → `404`.
5. **Баланс** — для `reserve`: `amount ≤ availableBalance` → иначе `409`.

> Важно: у операции `reserve` тело содержит только `{amount, rrn}`. Поля `currencyCode`, `dailyLimit` и `expiryDate` — свойства карты, а не тела запроса, поэтому при `reserve` они не валидируются заново.

## 2. Классы эквивалентности

### 2.1. Authorization: классы эквивалентности

| Аспект (поле) | Позитивный класс | Негативные классы | Представитель |
|---|---|---|---|
| Идентификация карты | PAN найден в CMS | PAN не найден · PAN невалидного формата · карта `DELETED` (не возвращается) | `4000001111111118` |
| Статус карты | `ACTIVE` | `INACTIVE` · `BLOCKED` · `EXPIRED` · `DELETED` | `ACTIVE` |
| Срок действия `expiryDate` (MMYY) | будущий месяц | текущий месяц (граница) · истёк (прошлый месяц) · неверный формат | `1230` (дек. 2030) |
| Сумма vs `dailyLimit` | `below` | `equal` (валидная граница) · `above` | 1 000 000 при лимите 15 000 000 |
| Сумма vs `monthlyLimit` | `below` | `equal` · `above` | 1 000 000 при лимите 300 000 000 |
| Сумма vs `availableBalance` | `below` · `equal` | `above` | 1 000 000 при балансе 100 000 000 |
| Сумма как значение | положительная | нулевая · отрицательная | 1 000 000 |
| Доступность CMS | доступен | недоступен → `05` `ISSUER_TIMEOUT` | — |
| Доступность Bin Lookup | доступен | недоступен → graceful degradation (fallback `issuerId`) | — |
| `terminalType` | `POS` | `ATM` · `ECOM` | `POS` |
| `mcc` | `grocery` | `restaurant` · `electronics` · `travel` | `5411` |
| Выходные значения (`responseCode`) | `00` | `05` · `12` · `14` · `51` · `54` · `61` | `00` |

**Правила.** Позитивные и негативные классы проверяются раздельно; один невалидный класс — один тест-кейс. Несколько валидных значений допустимо объединять, невалидные — нельзя. Типы классов: непрерывный диапазон (сумма vs лимит), дискретный набор (статус, `terminalType`, `mcc`), одно значение (`responseCode`).

### 2.2. Card-Management: классы эквивалентности

| Аспект (поле) | Позитивный класс | Негативные классы | Представитель |
|---|---|---|---|
| `bin` | из утверждённого списка `400000`–`400004` | неизвестный BIN · не 6 цифр · пусто | `400000` |
| `cardholderName` | непустая строка ≤ 255 | пусто · > 255 символов | `IVAN IVANOV` |
| `currencyCode` | `643` | неизвестный (`999`) · короче 3 символов | `643` |
| `dailyLimit` | положительный | нулевой · отрицательный | `15000000` |
| `monthlyLimit` | положительный | нулевой · отрицательный · меньше `dailyLimit` | `300000000` |
| `initialBalance` | положительный | нулевой · отрицательный | `100000000` |
| Генерируемый PAN | корректен по Луне | — (генерируется сервисом) | `4000001111111118` |
| Входной PAN | 16 цифр, корректная цифра Луна, найден | не найден · невалиден по Луне · не 16 цифр · не цифры | `4000001111111118` |
| `expiryDate` (MMYY) | `текущая дата + 3 года` | истёк · неверный формат (MM > 12, не 4 цифры) | `0929` |
| `status` в ответе | `ACTIVE` | `INACTIVE` · `BLOCKED` · `EXPIRED` · `DELETED` | `ACTIVE` |
| `status` (фильтр list) | одно из `ACTIVE`/`INACTIVE`/`BLOCKED`/`EXPIRED` | значение вне списка · `DELETED` (не отдаётся) | `ACTIVE` |
| `reserve amount` | `> 0` и `≤ availableBalance` | `0` · отрицательная · `> availableBalance` | `150000` |
| Резервирование PAN | существующий, `ACTIVE`, не истёк | неактивный · истёкший · `DELETED` | — |
| Дубли PAN при создании | уникальный PAN | существующий PAN → `409` | — |
| Пагинация | `limit ≥ 0`, `offset ≥ 0` | отрицательные значения | `limit=50`, `offset=0` |
| Выходные значения | `201` · `200` · `404` · `400` · `409` · `422` | — | `201` |

## 3. Граничные значения

Методика BVA: для каждой границы берутся три точки — **ON** (значение ровно на границе) и **OFF** (значения непосредственно ниже и выше). Единица измерения задаёт шаг: деньги — 1 копейка, счётчики — 1, строки — 1 символ. Точки, попадающие в уже покрытый соседний класс, не дублируются.

### 3.1. Authorization: граничные значения

| Граница | Тройка `{ниже, ON, выше}` | Ожидаемый результат |
|---|---|---|
| `dailyLimit` | `{limit − 1, limit, limit + 1}` | `<` и `=` → разрешено; `>` → `DECLINED`, `61` |
| `monthlyLimit` | `{limit − 1, limit, limit + 1}` | `<` и `=` → разрешено; `>` → `DECLINED`, `61` |
| `availableBalance` | `{balance − 0.01, balance, balance + 0.01}` | `≤ balance` → разрешено; `> balance` → `DECLINED`, `51` |
| `expiryDate` (MMYY) | `{прошлый MMYY, текущий MMYY, следующий MMYY}` | прошлый → `DECLINED`, `54`; текущий и следующий → разрешено |
| Учтённый лимит: `daily_amount + amount` | `{limit − 1, limit, limit + 1}` | переход через границу лимита за день |
| `amount` | `{−1, 0, 1}` | `≤ 0` → `DECLINED`, `12` / `30`; `1` → валидно |
| Длина PAN | `{15, 16, 17}` | 16 → валидно; 15/17 → `DECLINED`, `14` |
| Длина RRN | `{11, 12, 13}` | 12 цифр → валидно |
| Длина authCode | `{5, 6, 7}` | 6 символов `A-Z0-9` → валидно |
| Счётчик использования лимита (день/месяц) | `{0, 1, максимум}` | граница начала учёта |

### 3.2. Card-Management: граничные значения

| Граница | Тройка `{ниже, ON, выше}` | Ожидаемый результат |
|---|---|---|
| Длина PAN | `{15, 16, 17}` | 16 → валидно; иначе `400` |
| Контрольная цифра Луна | `{неверная, верная}` | верная → ок; неверная → `404` |
| `expiryDate` MMYY | `{текущий − 1 мес., текущий, текущий + 3 года}` | истёк → `422`; валиден → ок |
| `dailyLimit` | `{−1, 0, 1}` | отрицательный → `400`; `0` → допустимо |
| `monthlyLimit` | `{−1, 0, 1}` | отрицательный → `400` |
| `initialBalance` | `{−1, 0, 1}` | отрицательный → `400` |
| `reserve amount` vs `availableBalance` | `{balance − 0.01, balance, balance + 0.01}` | `≤ balance` → `200`; `> balance` → `409`/`422` |
| `reserve amount` | `{−1, 0, 1}` | `≤ 0` → `400` |
| `cardholderName` длина | `{254, 255, 256}` | 255 → валидно; 256 → `400` |
| `bin` длина | `{5, 6, 7}` | 6 → валидно; иначе `400` |
| `currencyCode` длина | `{2, 3, 4}` | 3 символа `643` → валидно |
| Пагинация `limit` | `{−1, 0, 50, 1000}` | отрицательный → `400`; `0` → пустой список |
| Пагинация `offset` | `{−1, 0, total − 1, total, total + 1}` | `≥ total` → пустой список |
| `count` генерации | `{−1, 0, 1, максимум}` | `≤ 0` → `400`/пустой результат |

## 4. Попарное тестирование

### 4.1. Модель Authorization

Модель — [`pict/model.txt`](pict/model.txt): 7 параметров, 4+3+3+3+3+3+4 = 23 значения.

```text
card_status:        ACTIVE, INACTIVE, BLOCKED, EXPIRED
amount_vs_daily:    below, equal, above
amount_vs_monthly:  below, equal, above
amount_vs_balance:  below, equal, above
expiry:             valid, current_month, expired
terminal_type:      pos, atm, ecom
mcc:                grocery, restaurant, electronics, travel

IF [card_status] <> "ACTIVE" THEN [amount_vs_daily] = "below"
    AND [amount_vs_monthly] = "below" AND [amount_vs_balance] = "below";
IF [expiry] = "expired" THEN [amount_vs_balance] = "below";
```

**Ограничения и их смысл.** Первое ограничение отражает порядок проверок: при неактивной карте транзакция отклоняется на шаге статуса, поэтому лимиты и баланс не проверяются — сочетания `INACTIVE`/`BLOCKED`/`EXPIRED` с `above` невозможны. Второе: по истёкшей карте списание невозможно, поэтому баланс не является ограничителем.

**Расчёт.**
- Полный перебор: 4 × 3 × 3 × 3 × 3 × 3 × 4 = **3888** комбинаций;
- Число пар значений (теоретическое): ((Σk)² − Σk²) / 2 = (23² − 87) / 2 = **226**;
- Допустимых комбинаций после ограничений: **864**;
- Достижимых пар значений: **206** (часть пар недостижима из-за ограничений);
- Строк в попарном наборе: **26**; непокрытых пар: **0** (покрытие 2-wise — 100 % достижимых пар).

> Покрытие всех пар проверено программно: [`pict/gen-auth.log`](pict/gen-auth.log).

### 4.2. Модель Card-Management

Модель — [`pict/model-card-management.txt`](pict/model-card-management.txt): **8 параметров**, по 2–4 значения на параметр (4+4+4+4+2+4+4+4 = 30 значений), 10 ограничений.

```text
operation:        create, get, patch, reserve
pan_validity:     valid_luhn, invalid_luhn, wrong_length, non_numeric
expiry_date:      future, current_month, expired, malformed
card_status:      ACTIVE, INACTIVE, BLOCKED, EXPIRED
deleted:          no, yes
currency_code:    valid, unknown, short, n_a
daily_limit:      positive, zero, negative, n_a
reserve_amount:   n_a, ok, insufficient_balance, non_positive

IF [operation] <> "reserve" THEN [reserve_amount] = "n_a";
IF [operation] = "reserve" THEN [reserve_amount] <> "n_a";
IF [operation] = "create" THEN [pan_validity] = "valid_luhn";
IF [operation] = "create" THEN [deleted] = "no";
IF [operation] = "create" THEN [card_status] = "ACTIVE";
IF [operation] = "create" THEN [expiry_date] = "future";
IF [operation] = "create" THEN [currency_code] <> "n_a" AND [daily_limit] <> "n_a";
IF [operation] = "patch" THEN [currency_code] <> "n_a" AND [daily_limit] <> "n_a";
IF [operation] = "get" THEN [currency_code] = "n_a" AND [daily_limit] = "n_a";
IF [operation] = "reserve" THEN [currency_code] = "n_a" AND [daily_limit] = "n_a";
```

**Ограничения и их смысл.** Модель описывает четыре операции одного ресурса — карты: `create`, `get`, `patch`, `reserve`; операции `list` и `delete` покрыты классами эквивалентности в разделе 5.4. Ограничения отражают структуру API: параметр `deleted` моделирует мягкое удаление (карта `DELETED`), поэтому для удалённой карты `get`/`patch`/`reserve` не находят ресурс; сумма резервирования применима только к `reserve`; тело с валютой и лимитом передаётся только в `create` и `patch` (для `get` и `reserve` этих полей в теле нет, они берутся из карты); при создании PAN генерируется сервисом (корректен по Луне), статус присваивается сервисом (`ACTIVE`), срок — «текущая дата + 3 года».

**Расчёт.**
- Полный перебор: 4 × 4 × 4 × 4 × 2 × 4 × 4 × 4 = **32 768** комбинаций;
- Число пар значений (теоретическое): ((Σk)² − Σk²) / 2 = (30² − 116) / 2 = **392**;
- Допустимых комбинаций после ограничений: **1673**;
- Достижимых пар значений: **332**;
- Строк в попарном наборе: **34**; непокрытых пар: **0** (покрытие 2-wise — 100 % достижимых пар).

> Покрытие всех пар проверено программно: [`pict/gen-cm.log`](pict/gen-cm.log).

### 4.3. Генерация наборов

**Основной путь — PICT (Microsoft):**

```bash
pict model.txt > cases.txt
pict model-card-management.txt > cases-card-management.txt
```

**Инструмент в среде может отсутствовать** — задание допускает резервный путь. Генерация выполнена эквивалентным жадным 2-wise-генератором [`pict/generate-pairwise.js`](pict/generate-pairwise.js):

```bash
node generate-pairwise.js model.txt > cases.txt
node generate-pairwise.js model-card-management.txt > cases-card-management.txt
```

Генератор разбирает ту же текстовую модель (параметры и `IF ... THEN ...` ограничения), перечисляет допустимые комбинации и жадно отбирает строки, максимизирующие число вновь покрытых пар. Результат идентичен по входу/выходу PICT: каждая строка — заготовка тест-кейса, покрытие всех пар — строгое. Файлы `cases.txt` и `cases-card-management.txt` закоммичены.

### 4.4. Маппинг строк набора в тест-кейсы

Каждая строка попарного набора проецируется в отдельный тест-кейс: `TC-AUTH-PW-01`…`TC-AUTH-PW-26` (26 строк из `cases.txt`) и `TC-CM-PW-01`…`TC-CM-PW-34` (34 строки из `cases-card-management.txt`). Значения параметров строки разворачиваются в конкретные данные (сумма, лимиты, баланс, статус, PAN) — методика развёртки приведена в разделах 5.0 и 5.3. Полное соответствие «строка → тест-кейс» приведено в разделах 5.3 и 5.6.

### 4.5. Ограничения техники и ручные дополнения

Покрытие всех пар **не гарантирует полноту**: взаимодействия трёх и более параметров остаются непроверенными. В набор вручную добавлены критичные сочетания, известные команде и не гарантированные 2-wise:

- **Authorization:** `BLOCKED` + истёкший `expiry` + нулевой баланс (проверка приоритета статуса над сроком и балансом); `EXPIRED` + `above dailyLimit` + `above balance` (строгий приоритет кода `54`); параллельное изменение баланса между `GET` и `reserve` (race condition, [`docs/architecture.md`](../architecture.md));
- **Card-Management:** `reserve` при `equal_balance` одновременно с истекающим сроком в текущем месяце (граница округления MMYY); `create` с дублирующимся PAN при полном совпадении прочих полей (проверка `409`).

Техника дополняет анализ требований, а не заменяет его: состав параметров и ограничений выведен из ТЗ, а не из инструмента.

## 5. Тест-кейсы

### 5.0. Тестовые данные (фикстуры)

Одинаковые данные используются во всех кейсах обоих сервисов — это обеспечивает воспроизводимость и трассируемость.

**Банк карт Authorization** (все PAN валидны по Луне, BIN `400000` → `issuerId = ISS001`):

| № | PAN | Свойство карты |
|---|---|---|
| 1 | `4000001111111118` | `ACTIVE`, базовая карта для позитивных и лимитных проверок |
| 2 | `4000002222222224` | `INACTIVE` |
| 3 | `4000003333333330` | `BLOCKED` |
| 4 | `4000004444444446` | `EXPIRED` (статус) |
| 5 | `4000005555555557` | `ACTIVE`, `expiryDate = 0925` (истёк) |
| 6 | `4000006666666663` | `DELETED` (мягко удалена) |
| 7 | `4000007777777779` | `ACTIVE`, `expiryDate = 0926` (текущий MMYY) |
| 8 | `4000008888888885` | `ACTIVE`, баланс `B = 1 000 000`, для проверки race condition |
| 9 | `4000009999999991` | `ACTIVE`, баланс `100 000 000`, для параллельной авторизации |
| 10 | `4000000000000000` | отсутствует в CMS (не найдена) |

**Базовые лимиты и баланс** (если в кейсе не указано иное): `dailyLimit = 15 000 000` (150 000 ₽), `monthlyLimit = 300 000 000` (3 000 000 ₽), `availableBalance = 100 000 000` (1 000 000 ₽), `currencyCode = 643`.

**Правило развёртки строки pairwise в данные.** Для каждой строки `cases.txt` выбирается сумма `A = 1 000 000` (10 000 ₽), а лимиты и баланс карты настраиваются так, чтобы получилось нужное соотношение: `below` → лимит/баланс = `A + 1`; `equal` → `A`; `above` → `A − 1`. Такой выбор допустим, так как лимиты и баланс — свободно задаваемые свойства карты, а не константы. Для строк с неактивным статусом или истёкшим сроком ограничение модели уже гарантирует `below` по всем трём параметрам.

**Соответствие коротких значений модели конкретным данным:**

| Параметр модели | Значение | Конкретные данные |
|---|---|---|
| `terminal_type` | `pos` / `atm` / `ecom` | `terminalType = POS` / `ATM` / `ECOM` |
| `mcc` | `grocery` / `restaurant` / `electronics` / `travel` | `mcc = 5411` / `5812` / `5732` / `3501` |
| `expiry` | `valid` / `current_month` / `expired` | `1230` / `0926` / `0925` |

### 5.7. Ручные дополнения к попарным наборам (критичные тройки)

Эти кейсы не гарантируются 2-wise-покрытием и добавлены вручную как известные критичные сочетания трёх и более параметров.

**TC-AUTH-MAN-01 — приоритет статуса над сроком и балансом**
- **Требование:** `tz/04-authorization.md` §2, шаги 2–6 (порядок проверок).
- **Вид/уровень:** негативный, низкоуровневый.
- **Предусловие:** карта `BLOCKED`, `expiryDate = 0925` (истёк), `availableBalance = 0`.
- **Шаги:** `POST /api/internal/authorize` на `amount = 1000`.
- **Ожидаемый результат:** `DECLINED`, `declineReason = "CARD_BLOCKED"` — статус проверяется первым, несмотря на одновременно истёкший срок и нулевой баланс.
- **Постусловие:** баланс неизменен (0). **Приоритет:** высокий.

**TC-AUTH-MAN-02 — приоритет срока действия над лимитами и балансом**
- **Требование:** `tz/04-authorization.md` §2, шаг 3.
- **Вид/уровень:** негативный, низкоуровневый.
- **Предусловие:** карта `ACTIVE`, `expiryDate = 0925`, `dailyLimit = 999 999`, `availableBalance = 999 999`.
- **Шаги:** `POST /api/internal/authorize` на `amount = 1 000 000` (превышает и лимит, и баланс).
- **Ожидаемый результат:** `DECLINED`, `responseCode = "54"` — проверка срока опережает проверку дневного лимита и баланса.
- **Постусловие:** баланс неизменен. **Приоритет:** высокий.

**TC-AUTH-MAN-03 — race condition при резервировании**
- **Требование:** `docs/architecture.md` — резервирование не атомарно; `tz/04-authorization.md` §2.
- **Вид/уровень:** негативный, низкоуровневый.
- **Предусловие:** карта №9 `4000009999999991` `ACTIVE`, `availableBalance = 1` (минимальный ненулевой).
- **Шаги:** отправить две авторизации по одной карте на `amount = 1` и `amount = 2` одновременно (параллельно).
- **Ожидаемый результат:** ровно одна транзакция `APPROVED`; вторая — `DECLINED`, `responseCode = "51"`; итоговый `availableBalance ≥ 0` (баланс не уходит в минус). Допускается, что при гонке обе отклонены; недопустимо — обе одобрены при балансе 1.
- **Постусловие:** `availableBalance ∈ {0, 1}`, отрицательного значения нет. **Приоритет:** высокий (недетерминированный кейс, помечается как flaky-риск).

**TC-AUTH-MAN-04 — уникальность RRN при совпадении timestamp**
- **Требование:** `tz/04-authorization.md` §6 — уникальность RRN, формат `{YDDD}{HH}{mm}{ss}{seq}`.
- **Вид/уровень:** негативный, низкоуровневый.
- **Предусловие:** карта `ACTIVE`, баланс достаточен для двух транзакций.
- **Шаги:** выполнить две успешные авторизации в пределах одной секунды.
- **Ожидаемый результат:** оба RRN — 12 цифр и различаются компонентой `seq`; дублирования RRN нет.
- **Постусловие:** обе транзакции записаны. **Приоритет:** средний.

**TC-CM-MAN-01 — дубль PAN при создании**
- **Требование:** `tz/05-card-management.md` §2 (POST), `docs/api-spec.md` — `409`.
- **Вид/уровень:** негативный, низкоуровневый.
- **Предусловие:** карта с PAN `P` создана ранее.
- **Шаги:** два `POST /api/cards` с одинаковым телом при детерминированном seed генератора (гарантирует одинаковый PAN).
- **Ожидаемый результат:** первый — `201`; второй — `409`, карта не создаётся.
- **Постусловие:** в БД одна карта с PAN `P`. **Приоритет:** высокий.

**TC-CM-MAN-02 — резерв ровно на весь баланс при истекающем сроке**
- **Требование:** `tz/05-card-management.md` §5; формат `expiryDate` MMYY.
- **Вид/уровень:** негативный, низкоуровневый.
- **Предусловие:** карта `ACTIVE`, `expiryDate = 0926` (текущий MMYY), `availableBalance = 100 000 000`.
- **Шаги:** `POST /api/cards/{pan}/reserve` `{amount:100000000, rrn:"012345678901"}`.
- **Ожидаемый результат:** `200`; `availableBalance = 0` — карта действует в текущем месяце включительно, списание на полную сумму допустимо.
- **Постусловие:** баланс = 0. **Приоритет:** средний.
