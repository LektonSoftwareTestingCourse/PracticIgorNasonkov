## 1. Область тестирования и подход

**Область.** Система СМП целиком: 11 микросервисов, PostgreSQL и RabbitMQ. Глубина проверок распределена по трём слоям:

- **Проектный слой** — стратегия и настоящий план (вся система);
- **Ядро** — Authorization (`POST /api/internal/authorize`) и Card-Management (CRUD, генерация, `/reserve`): полный набор техник — классы эквивалентности, граничные значения, попарное тестирование;
- **Периферия** — Gateway, Switch, Terminal Simulator, Merchant Simulator, Bin Lookup, Notification Service, Transaction Logger, Web Dashboard: классы верхнего уровня и чек-листы.

**Подход.** Чёрный ящик по спецификациям. Основные техники — классы эквивалентности и граничные значения (базовая пара), для ядра — дополнительно попарное тестирование с моделью PICT и ограничениями. Приоритет риск-ориентированный: сначала decline-сценарии и целостность записи транзакций, затем валидация форматов, затем агрегаты и визуализация. Негативные проверки выполняются после подтверждения позитивного сценария.

## 2. Критерии входа

- Развёрнут стенд: `docker compose up -d` поднимает 11 сервисов + PostgreSQL + RabbitMQ без ошибок;
- `docker compose ps` — все контейнеры в состоянии `Up` (healthy);
- Требования согласованы: ТЗ [`tz/04-authorization.md`](../../tz/04-authorization.md), [`tz/05-card-management.md`](../../tz/05-card-management.md) и [`docs/api-spec.md`](../api-spec.md) актуальны;
- Тестовые данные подготовлены: сгенерировано не менее 100 карт (`POST /api/cards/generate`) по пяти BIN (`400000`–`400004`);
- Доступны артефакты генерации: `pict/model.txt`, `pict/model-card-management.txt`, `pict/cases.txt`, `pict/cases-card-management.txt`;
- Пройдено дымовое тестирование (см. [`checklists.md`](checklists.md), раздел 1).

---

## 3. Критерии выхода

- Отсутствие открытых дефектов критического и высокого уровней;
- Покрытие ключевых бизнес-полей ядра ≥ 95 % (все классы эквивалентности имеют представителя, все границы покрыты тройками ON/OFF);
- Сгенерированные попарные наборы покрывают **100 % достижимых пар значений** (для Authorization — 206 из 206 при 2 ограничениях модели, для Card-Management — 332 из 332 при 10 ограничениях модели);
- Каждый тест-кейс имеет идентификатор, связанное требование и источник (класс / граница / строка pairwise);
- Пройден лист самопроверки практики 2;
- Отчёты о дефектах в артефакт не входят — оформляются в модулях 7–8.

## 4. Критерии приостановки и возобновления

**Приостановка** — при обнаружении блокирующего дефекта критического уровня:

- не проходит health-check любого сервиса ядра (Authorization, Card-Management, Switch);
- позитивный сценарий авторизации не выполняется (любая транзакция отклоняется) — на этом фоне негативные проверки неинформативны;
- одобренная транзакция не фиксируется в Transaction Logger (`Publisher Confirm` не получен, reversal не срабатывает);
- PostgreSQL или RabbitMQ недоступны.

**Возобновление** — после устранения блокирующего дефекта и подтверждения прохождения позитивного сценария; прогон возобновляется с дымового чек-листа, чтобы исключить накопленные побочные эффекты.

## 6. Риски и меры

| Риск | Вероятность | Последствие | Мера |
|---|---|---|---|
| Модель PICT без ограничений → невозможные сочетания | Средняя | Набор непригоден для прогона | Обязательные `IF ... THEN` ограничения в обеих моделях; проверка покрытия |
| Покрытие пар выдано за полноту | Средняя | Критичные тройки не покрыты | Ручное добавление критичных сочетаний в `test-design.md` |
| Поздние правки правил валидации/CMS | Средняя | Повторный прогон и пересборка модели | Версионирование модели в репозитории; пересмотр набора при изменении требований |
| Неразличимые причины отказа | Низкая | Невозможна локализация дефекта | Один невалидный класс — один тест-кейс |
| Недоступность PICT в окружении | Средняя | Генерация набора невозможна | Резервный генератор `generate-pairwise.js` (2-wise), `allpairspy`/pairwise.org |
| Eventual consistency Logger | Средняя | Ложные дефекты «нет записи» | Учитывать асинхронную доставку через RabbitMQ; проверять с задержкой |

## 7. Метрики

- **Доля выполненных тест-кейсов** — выполнено / запланировано;
- **Покрытие классов эквивалентности** — доля классов с представителем;
- **Покрытие границ** — доля границ с тройками ON/OFF;
- **Покрытие пар значений (2-wise)** — покрыто / достижимо, целевое значение 100 %;
- **Число открытых дефектов** — в разрезе уровней (критический / высокий / средний / низкий);
- **Approval rate** — доля `APPROVED` транзакций, сверяется с ожиданиями сценариев симулятора;
- **Доля отклонений по причинам** — распределение `DECLINED` по `declineReason`/`responseCode`, сопоставляется с моделью.
